## [Unreleased]

### Added

- The Spring Boot starter builds a `Muster` bean from the rules of the application. Rule classes with `@Rule` in the packages of the application, the packages that `@SpringBootApplication` scans, become beans without `@Component`, named after their class, and their annotations and conditions, such as `@Lazy` or `@ConditionalOnProperty`, apply as they do to components; a rule elsewhere joins once it is a bean. A rule bean must be a singleton and be declared with a class that carries `@Rule`, not as a `BusinessRule`, so that Muster can read its id. Two rule beans of one class, or a rule bean behind a proxy based on interfaces, stop the application and say why. A `Muster` bean of the application's own replaces the starter's.
- `@Rules` checks the input of a method before the method runs: against the rules it lists, in their order, and for a rule target the rules that bind to its class by type, less the rules it excludes, in the mode it gives or the Muster's. Muster finds it as Spring finds `@Transactional`, also on an interface method and as a meta-annotation, and checks the rules however a call reaches the method: through an interface, a bridge method or a base class, and on a bean that is a proxy based on interfaces itself, such as a Spring Data repository. The input is the only parameter of the method; a method with rules that takes no parameter or more than one, that is not public, or that is static or final stops the application, and so does a rule it lists that is not registered. Logs name the method, as in `VehicleService.save(SaveVehicle)`. A call from one advised method to another with the same input checks the rules again; a call within the same bean, through `this`, passes no proxy and checks none. Method validation with `@Validated` may run after the rules, a call answered from the cache of `@Cacheable` checks none, and an `@Async` method checks them on its own thread. Rules apply also to calls made while the application starts, such as from code that seeds data, to beans created later, such as lazy ones, and with lazy initialization. The advice applies also where neither Spring Boot's AOP support nor transaction management creates proxies.
- The public methods of a `@Service` bean that take a rule target check the rules that bind to its class by type without `@Rules`, before they run. A `@Service` method that takes a rule target among other parameters stops the application: rules check one input, so it takes a command object instead. Other beans, such as controllers and repositories, check only methods with `@Rules`, so that rules run where the transaction is, and once.
- Rules run inside the transaction of their method. Muster's advice comes last, and the starter moves the transaction advice one step ahead of it, however the application is configured, unless the application gives `@EnableTransactionManagement` an order of its own; `muster.transaction.reorder-advisor=false` turns that off. Either way, the application does not start, or a bean created later is not created, if the transaction advice would not run around Muster's, and the error says how to fix it, and transactions woven in with AspectJ stop it too. Spring's transaction support is optional. A method that requires a transaction, such as `@Transactional` with the default propagation, fails if its rules run with no transaction active.
- `muster.rules.<rule id>.enabled=false` switches a rule off without a new build, also as an environment variable such as `MUSTER_RULES_VEHICLE_NAMEUNIQUE_ENABLED=false`. A key under `muster.rules` that switches no rule, such as a misspelled id, stops the application and names the rule ids, and so does a key set to nothing. `muster.mode` sets the mode: `fail-fast`, the default, or `collect-all`. IDEs know both properties.
- Rules learn who makes a call from Spring Security, when the application has it, through its `SecurityContextHolderStrategy` bean if it defines one; a call that is anonymous or not authenticated has no caller. The locale is the one `LocaleContextHolder` holds, as Spring MVC sets it for a request, and otherwise the default locale of the JVM. A `Supplier<Principal>` or `Supplier<Locale>` bean of the application replaces either; a raw `Supplier` does not.
- The starter resolves the messages of violations from the message source of the application, through a `MessageResolver` bean: a code names a template, such as `vehicle.name-taken=The name {name} is taken` in `messages.properties`, whose `{name}` placeholders take the client arguments; without a template, the message is the code. An exception handler of the application can inject the bean, and a `MessageResolver` bean of the application replaces it. A message source that formats every message with `MessageFormat`, as `spring.messages.always-use-message-format=true` makes it, stops the application, since `MessageFormat` rejects the placeholders.
- In a Spring MVC application, the starter answers a `BusinessRuleViolationException` with problem details (RFC 9457). Violations of one category get its status: 403 for `FORBIDDEN`, 404 for `NOT_FOUND`, 409 for `CONFLICT`, and 422 for `INVALID_STATE` or no category; violations of different categories get 422, or the client error that `muster.problem-details.mixed-status` sets. The `violations` property lists each violation's `code`, its `message` in the locale that rules see, its `target` and `category` if it has them, and its client arguments as `args`, which Jackson writes even when the application leaves out empty values. The rule id, internal arguments and the severity stay out of the response; the violations are logged at DEBUG. The handler has the order 0, as Spring Boot's own problem details do, so a handler of every `Exception` in controller advice without an order of its own does not turn violations into server errors. A controller advice that names `BusinessRuleViolationException` in an `@ExceptionHandler`, in the context of the application or in a parent one, replaces it.
- What the starter adds to a service method, measured with JMH and held to a budget: about 120 ns and 96 bytes a call, most of it the cost of a Spring AOP proxy. The published benchmark results are now the median of five forks, with the range of the others, since a fork now and then settles on other compiled code than the others, nearly always slower.
- Releases of `me.yakar.muster:muster-spring-boot-starter` on Maven Central, signed, with sources, API docs and a CycloneDX SBOM. `muster-bom` aligns its version with the core's. The starter's optional integrations, Spring Security, Spring's transactions and Spring MVC, are not dependencies of it: it uses them when the application has them.
- The starter works with Spring Boot 4.0.8 and later, 4.1 included. It is built against the oldest version it supports, so it never pulls an application up to a newer Spring Boot.
- `muster.binding(type)` builds a `Binding`: the rules it lists, and for a rule target the rules that bind to its class by type, less the rules it excludes, in a mode and under a name of its own. A binding for a final type prepares its rules when it is built; for another type, on the first check of each class. A listed rule cannot require an excluded rule; a rule bound by type that requires one is left out and logged.
- `muster.check(target, mode)` checks a rule target in a mode other than the Muster's, without a second Muster. The rules of a class are still bound once.
- `RuleContext.forRule(Class)` and `RuleContext.builder(Class)`, which read the rule id from `@Rule`, so a rule's test does not repeat it.
- `MessageResolver` turns the code and the client arguments of a violation into a message in the caller's locale, at the edge of the application; it never sees internal arguments. `MessageResolver.ofTemplates(lookup)` resolves messages from templates of your own, in which `{name}` stands for a client argument, written with `String.valueOf`. A name that is not a client argument stays as it is, `{{` and `}}` write a single brace, and apostrophes need no escaping. Without a template, the message is the code. `MessageResolver.ofResourceBundles(locale -> ResourceBundle.getBundle("com.example.messages", locale))` reads the templates from resource bundles that your own module loads, so they are found on the module path too. It needs a base bundle and never falls back to the default locale of the JVM: a French client of a Turkish server gets the base bundle, not the Turkish one.
- The violation category `FORBIDDEN`, for a caller who may not act on the data a request refers to, such as a task that only its owner may close.

### Changed

- **Breaking:** A chain runs its rules in the order it lists them, not in the order of their ids, so cheap rules can run first. Before each listed rule it runs the rules that rule requires and that have not run yet, each after its own requirements, ordered the same way: listed ones in the order they are listed, the others in the order of their ids. `muster.check(target)` still runs rules in the order of their ids. The same chain may now report another violation in `FAIL_FAST` mode, and the violations of `COLLECT_ALL` mode may come in another order.
- **Breaking:** `Category` has a new constant, `FORBIDDEN`, listed first so that the categories follow the order of the status codes they stand for. A `switch` over `Category` without a `default` no longer compiles until it handles `FORBIDDEN`.
- **Breaking:** A violation code cannot contain whitespace, spaces such as the no-break space, control characters, format characters such as the zero-width space, or unpaired surrogates, which break message keys or hide in them unseen. A code is otherwise free, for example `VEHICLE_NAME_TAKEN`. A violation serialized by 0.1.0 with such a code no longer deserializes.
- **Breaking:** An argument name, client or internal, follows the same rule as a code and cannot contain a brace either, so that a message template can refer to every client argument as `{name}`. A violation serialized by 0.1.0 with such a client argument name no longer deserializes.
- The Javadoc of `RuleContext.locale()` no longer suggests comparing names in the caller's locale, which lets the same name pass for one language and fail for another; it says to normalize stored data in one fixed locale.
- When rules that require a disabled rule are still enabled, Muster names all of them at once, also those that require it through other rules, so one change to the configuration fixes the setup.
- A violation that has no client arguments, or no internal ones, allocates no map for them, so a failing check allocates less.

### Fixed

- The purls in the SBOM of `muster-core` no longer carry a `project_path` qualifier, which named the module's path in Muster's build and no published artifact has.

## [0.1.0] - 2026-10-23

### Added

- Violations that keep client arguments, which reach messages and responses, apart from internal arguments, which never leave the application.
- `BusinessRuleViolationException`, thrown once per check with the violations found; its message lists codes only.
- Rule results: a rule either passes or fails with one or more violations.
- Violation categories (`NOT_FOUND`, `CONFLICT`, `INVALID_STATE`), an optional target field, and a severity. Internal arguments are dropped when a violation goes through Java serialization.
- The rule contract: a rule implements `BusinessRule<T>`, carries a stable id with `@Rule`, and can opt out of a call with `appliesTo`.
- A rule context that tells a rule who makes the call and in which locale. `RuleContext.forRule(id)` creates one for testing a rule on its own. `toBuilder()` derives the context of the same rule for another call.
- `Muster`, the engine: rules are registered as instances or created by a `RuleFactory`, and every rule is validated when Muster is built. `muster.chain(...)` prepares a `RuleChain` once; each check runs the rules that apply and throws a single exception with the violations, as the check mode decides.
- `@RequiresRule`: a rule runs after the rules it requires, and only if they passed. Chains add required rules they do not list. Each rule class declares its own requirements; a rule that would lose them to inheritance is rejected.
- Binding rules by type: an input that implements `RuleTarget` is checked with `muster.check(input)` by every enabled rule whose input type accepts its class. Muster warns when no rule binds to a target.
- Switching rules off by id with `disable`, without changing code.
- Check modes: `FAIL_FAST`, the default, stops at the first violated rule; `COLLECT_ALL` reports the violations of every rule. Muster has a mode, and a chain can override it with `withMode`.
- `muster-core` depends only on the JSpecify annotations, which carry the API's null contract.
- Releases of `me.yakar.muster:muster-core` and `me.yakar.muster:muster-bom` on Maven Central, signed, with sources, API docs and, for the core, a CycloneDX SBOM.
- The API is split by audience: `me.yakar.muster` for the calling side, `me.yakar.muster.rule` for writing rules, `me.yakar.muster.spi` for integrations.
- JMH benchmarks in `muster-benchmarks`, which is not published, measure what a check adds to a call, also from many threads at once. `./gradlew jmh` runs them.
- The measured cost of a check and the budget it is held to, in `docs/benchmarks`, with a chart in the README. A passing check of 20 rules adds about 100 ns over calling them by hand.
