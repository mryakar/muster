= Checking inputs
:description: How an application without Spring builds Muster, and checks an input against a chain of rules, the rules of its type, or both.
include::partial$javadoc.adoc[]

An application builds one link:{javadoc-core}/Muster.html[`Muster`] with its rules, and checks each input against some of them: the rules it lists, the rules that bind to the type of the input, or both.

The application creates its rules and hands them to the builder.
Where a dependency injection container creates them instead, the builder takes their classes and a link:{javadoc-core}/spi/RuleFactory.html[`RuleFactory`], which asks the container for each one when `Muster` is built.
The caller and the locale come from suppliers that xref:core/context.adoc[] describes, and the listener is the subject of xref:core/listeners.adoc[].

A mistake in the setup, such as two rules with the same id or a rule that requires one nobody registered, stops the application when `Muster` is built, or when a chain or a binding is created, rather than on the first call that would meet it.
`Muster` is meant to live as long as the application, and to be shared by every thread.

A command that passes goes on to the repository; one that does not makes `check` throw, and the vehicle is never added.
In an application with a database, the check is the first step inside the transaction of the operation, so that the rules read the data that the operation then changes.

A rule reads the data but does not lock it, so two calls that create a vehicle named Atlas at the same moment can both pass the check.
The unique constraint of the database stays the last guard; the rule is what gives the client a clear answer in the usual case.

Without Spring, the application opens the transaction itself and puts it where the rules and the repositories find it, on the thread of the call, as it does with the caller in xref:core/context.adoc[]:

[source,java]
----
include::example$plain-java/java/example/plain/Transactions.java[tag=transaction,indent=0]
----

With JDBC, the transaction is a connection whose auto-commit is off, and a rule that queries the database reads through that connection, so it sees what the transaction wrote before the check, and the writes that follow it are part of the same transaction.
A rejected check throws before anything is written, and the rollback ends the transaction; `remove` leaves nothing behind on a thread of a pool, and `close` gives the connection back.
A second transaction on the same thread is refused rather than mixed with the first.

== The order of rules

The order of a chain is the order of its list, with each rule's requirements moved in front of it.
Rules of a type have no list, so they run in the order of their ids, again after their requirements; a binding runs the rules it lists before them.
The order does not change from call to call.
It matters in fail-fast mode, which stops at the first violated rule: list the rules that cost nothing, such as the format of the plate, before those that query the database.

== Logging

Muster logs through the `System.Logger` named `me.yakar.muster`, which writes to `java.util.logging` unless the application routes it elsewhere:

* At `INFO`, the rules a chain or a binding adds because a listed rule requires them, and the rules it leaves out because they require an excluded one.
* At `DEBUG`, which `java.util.logging` calls `FINE` and hides unless it is switched on, the rules of each class bound by type, when it is first checked.
* At `WARNING`, a class that no rule binds to, which usually means that a rule was never registered, each rule that is switched off, and, on its first collection, a rule that checks the elements one by one because it does not override `checkAll`, as xref:core/collections.adoc[] describes.
