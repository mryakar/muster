= Writing a rule
:description: A business rule of Muster: a class with an id that checks one kind of input and reports what is wrong with it as violations.
include::partial$javadoc.adoc[]

A business rule is a class of its own that checks one kind of input and reports what is wrong with it.
This guide follows an application without Spring that creates and renames the vehicles of a fleet.
Every sample is part of that application, which runs on every build of Muster and fails if Muster does not answer as the guide says.

== A rule

The fleet must not have two vehicles with the same name:

[source,java]
----
include::example$plain-java/java/example/plain/VehicleNameUnique.java[tag=rule,indent=0]
----

The rule checks `VehicleFields`, which both the command that creates a vehicle and the one that renames it carry, so one rule guards both.
Muster reads the type from link:{javadoc-core}/rule/BusinessRule.html[`implements BusinessRule<VehicleFields>`], which is why a rule is a class with a name rather than a lambda.

`vehicle.name-unique` is how the rest of the application refers to the rule: the client receives it as the code of the violation, the configuration names it to switch the rule off, and the logs print it.
Moving or renaming the class changes none of that, so choose the id as carefully as a column name.

The rule gets the vehicles in its constructor and asks them on each call.
One instance serves every call, from every thread that checks, so the rule and what it is given must be thread-safe, and nothing of one call stays in its fields.

`check` answers with link:{javadoc-core}/rule/RuleResult.html[`RuleResult.passed()`], or with a failed result that holds the violations.
Rejecting the call is Muster's job, once every rule that should run has run, as xref:core/errors.adoc[] describes.
When the vehicles cannot be read at all, the exception of the repository propagates as it is: that is a failure of the application, not an answer about the name.

== Violations

[source,java]
----
include::example$plain-java/java/example/plain/VehicleNameUnique.java[tag=violation,indent=0]
----

The violation starts from the context of the rule, which stamps it with the rule's id.
It holds no text: the edge of the application writes the message, in the language of whoever made the call, from what the violation carries:

* The code, here the rule's id.
A rule that can fail for two different reasons gives each its own code, with `ctx.violation(code)`.
* Client arguments, which the message refers to and the client receives, such as the name that is taken.
* Internal arguments, which only the application sees, in its logs and its code.
* The target: here `name`, the field of the command that the client should correct.
* The category: here `CONFLICT`, the kind of problem, from which an HTTP edge picks the status.
* The severity, which is `ERROR` for every violation today: each one rejects the call.

The vehicle comes from `VehicleExists`, which this rule requires, as xref:core/values.adoc[] explains.
A user who may not rename the vehicle is told so, and never who owns it, while the logs of the application still have the owner.
A rule leaves the category out when no category fits; xref:core/errors.adoc[] shows how each one is answered.

== Rules that do not apply

Some rules make sense only for some calls, which the context of the call tells before the input is read.
The xref:core/context.adoc#locale[format of a licence plate] is checked only where the rule knows the format.
A rule that does not apply is skipped, which is neither a pass nor a failure, and the rules that require it are skipped as well.
