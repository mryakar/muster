== The exception

A rejected call ends in a link:{javadoc-core}/BusinessRuleViolationException.html[`BusinessRuleViolationException`], which `check` throws once the rules that should run have run.
In fail-fast mode it holds what the first rule to find a problem found, and in collect-all mode what every rule found, in the order the rules ran.

A rejected call is an ordinary outcome, not a bug, so the exception is cheap to throw: it carries no stack trace.
It also keeps the values of the arguments out of its message, which names only the codes, so that logging it leaks nothing.
Catch it where the call came in, and answer the caller from its violations.

Other exceptions mean something else:

* A mistake in the setup fails when link:{javadoc-core}/Muster.html[`Muster`], a chain or a binding is built, with an `IllegalArgumentException` or an `IllegalStateException` that names the mistake.
* A mistake in a rule fails the check itself: a rule that returns `null` causes a `NullPointerException`, and a rule that reports a violation created for another rule an `IllegalStateException`.
* A collection with a `null` element, or with elements of different classes where rules bind by class, fails with a `NullPointerException` or an `IllegalArgumentException`.
* An exception that a rule throws, such as one of a database that cannot be reached, comes out of the check as it is.

A plate in the wrong format has no category and is answered with 422.
So is a call rejected for problems of different kinds, such as a taken name and a wrong plate at once, since no single status fits both.

[source,java]
----

----

The handler of the request catches the exception, answers with the status, and writes the entries with its JSON library; the starter sends the same fields inside problem details.
The violation itself is not sent: its internal arguments are for the application, and its `toString`, meant for logs, prints them.
